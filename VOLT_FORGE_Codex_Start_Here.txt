PROJECT CONTEXT
We are three BITS Pilani students, two EEE and one Chemical Engineering student, preparing TELIPORT Case Study 2: a reusable digital platform for designing battery energy systems. Build a research prototype that configures a module, checks subsystem consistency, simulates coupled behaviour, searches for requirement violations, compares physically permitted repairs, and preserves traceable evidence.

The initial object is one single-chemistry 1s4p LG M50T NMC research module. Stationary DC backup is a future application context. A four-cell parallel group remains at cell-level voltage; it is not a complete 12 V or 48 V backup battery.

CURRENT STATE

SUBSEQUENT WORKFLOW (FUTURE ASSIGNMENTS)

STAGE B: MODEL AND VALIDATION
Implement the actual electrical ladder network and an identifiable low-order cell model. Start with electrical behaviour, then add coupled thermal behaviour. Use one-RC equivalent circuits when characterization supports them. Track per-cell SOC and polarization states. Keep parameter sources and validity ranges explicit.

Use a surface-equivalent thermal network unless the available evidence supports a core/surface model. Check heat accounting and avoid counting electrical losses twice. Mechanical scope begins with placement, clearances, conductor lengths, mass and volume. Represent sensing delay/bias and module-level current derating only as justified.

Verify current conservation, physically sensible limits, analytical symmetric cases and numerical convergence. Fit on calibration records and assess untouched runs. Report per-channel error, bias and maximum error, not only a voltage fit. Set acceptance limits before fitting based on measurement uncertainty and the engineering decisions we intend to distinguish. If model uncertainty is as large as a claimed repair advantage, do not rank that repair as superior.

Exit evidence: measured-versus-predicted plots, held-out errors, parameter provenance, documented limits and a conclusion about which comparisons are trustworthy. Passing software tests alone is not scientific validation.

STAGE C: DETERMINISTIC FAILURE AND REPAIR WORKFLOW
Define sourced requirements with IDs, limits, units and operating domains. Reject invalid configurations. Run corners and a reproducible scenario sample before using ML.

Compare A0 (original), A1 (engineering heuristic) and A2 (a selected candidate from a finite repair catalogue). Re-evaluate every candidate on common scenarios. Candidate changes must map to real component/control choices. Begin near the measured interconnect/configuration domain. New geometry and new cooling arrangements require separate evidence.

Record usable energy, unmet demand after derating, current imbalance, temperature peak/spread, limit violations, computation time, and sourced or explicitly assumed cost/mass. Do not let a zero-power design win merely because it stays cool. Preserve every violating scenario as a regression case. Include seeded unit/assumption conflicts to test the interface checker.

Exit evidence: one reproducible end-to-end case from requirement violation to two compared alternatives, with uncertainty and trade-offs. If no honest violation exists within the chosen domain and sourced limits, report that and revisit the use case; do not invent a dramatic failure.

STAGE D: TEST WHETHER AI EARNS ITS PLACE
Measure the cost of simulation and the size of the search space. Compare enumeration or sampling against a small surrogate-guided search, such as a Gaussian process, only when justified. Do not adopt PPO solely because the team used it in Nebula.

Fix identical search domains, budgets and assessment scenarios. Include surrogate fitting/setup cost in end-to-end timing. Use multiple seeds where the method is stochastic. Confirm suggested failures and repairs with the physics engine. Distinguish verification by the same model from independent experimental validation.

Exit evidence: an honest comparison of violations found, verified design quality, simulator calls and total runtime. Retain a simpler method if it performs as well. An AI benefit remains a hypothesis until these comparisons support it.

STAGE E: INTEGRATE THE INTERFACE
Connect a lightweight UI to the verified runner. Useful screens are module configuration, baseline results, stress-case inspection, alternative comparison and evidence export. The UI reads actual result records. A replay must identify itself as a replay, and a scripted UI concept must identify itself as illustrative.

Keep simulation independent of the UI. Save requirements, designs, scenarios, model/parameter versions, source hashes, seeds and results. Changed assumptions invalidate dependent results. Display measured, simulated-in-domain and extrapolated outputs distinctly. An LLM explanation, if added later, must reference structured evidence and cannot decide whether a design meets a limit.
